## 1. El problema que resuelve

La marca paga por una publicación y a los tres meses no queda rastro de ella. Sin evidencia, la campaña
no se puede demostrar ni ante el cliente ni ante una auditoría.

| Tabla | Qué resuelve |
|---|---|
| `deliverables` | Qué debe entregar este creador concreto |
| `deliverable_versions` | Cada reenvío, **solo inserción** |
| `content_reviews` | El veredicto, **solo inserción** |
| `publications` | El enlace publicado y su verificación |
| `publication_evidence` | La prueba: captura, snapshot de API, comprobación HTTP |
| `permanence_checks` | ¿Sigue vivo el post? **Solo inserción** |

---

## 2. Cuatro decisiones

**Las versiones no se sobrescriben.** Cada reenvío es una fila. Es lo que permite responder *"cuántas
vueltas costó esto"* — dato que alimenta el Creator Score y el conteo de las 2 rondas que incluye tu
precio.

**Solo la corrección consume ronda.**

```sql
consumes_round = 0 OR outcome = 'changes_requested'
```

Una aprobación no puede gastar una de las dos rondas que le cobras al cliente. Parece obvio hasta que
alguien lo marca por error en una pantalla.

**El mismo post no puede reclamarse dos veces.** `url_fingerprint` es único y se calcula sobre la URL
**normalizada** — sin `utm` ni parámetros de campaña. Dos creadores reportando el mismo enlace con
distintos parámetros chocan igual. Se guarda el hash y no la URL cruda porque una URL puede pasar de 500
caracteres y un hash siempre mide lo mismo, así que se indexa bien.

**Una evidencia sin contenido no es evidencia.** Archivo, payload o estado HTTP: al menos uno de los
tres. Sin esa regla se pueden crear filas que dicen *"verificado"* y no enseñan nada.
